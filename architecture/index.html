The Story Department

Nineteen agents in five departments, read as a company. Code is management: every step script decides the order, hands out briefs, assembles, counts and checks. Agents are specialists: each gets one brief and returns one typed object. Nobody edits a file; nobody reads another agent's answer. The chart below is who reports to whom; the flow after it is one book going through a typical run, from the EPUB to a delivered episode master. Updated 2026-09-24: the reference bible (refs) and the episode line are departments with runners.

Signatures, five — and what is judged instead

Each is a file or a flag the ledger records. A sentence in chat signs nothing.

  • MONEY · any paid cost kind · --approved=<kind> · never retires (these lines spend none)
  • PUBLISH · every public write · --approved=publish · retirable per series × platform
  • OVERRIDE · any waiver of a machine gate · never retires
  • Synthetic declaration · series.json synthetic · typed once
  • RENDER_HOLD · a file; the brake, not a gate

Judged, not signed: LOOK, PLAN, EYE (board, takes) and MASTER are signed by judge:<name>@<version> from day one (decision 2026-09-24-automate-the-taste-gates). A judge signs pass or flagged, never fault; it never waives. The brick

One rule that regenerates every department's table.

One work-order row per (book, department, unit). A row is queued when every row it requires (the registry's edge) is done and its declared inputs exist on disk. A runner claims the earliest queued row of its department and runs the registry's steps for that unit; the row's state is whatever the run's last event says. The department's last step writes the unit's manifest.json, which is the next department's declared input. Every department's table is stages.yaml applied to work_orders; the disk stays the truth of a step, the events table the journal, the row their projection — written from one place, rebuildable from disk.

How a department is driven

The table is the queue; the runner is unchanged; the board only writes orders.

tick(conn)    rows from the registry × the slate (INSERT OR IGNORE) · blocked → queued when requires are done
              and in: exist · RENDER_HOLD → holds · expired leases → stale
claim(conn)   UPDATE work_orders SET state='running', claimed_by=?, lease_until=now+15m
              WHERE id = (SELECT id FROM v_queue WHERE stage=? LIMIT 1) RETURNING *
run           step_runner.run_steps(ctx, steps)          -- unchanged; add_event upserts the row
settle        the last event's word; outputs, gpu_seconds, cost from what the run wrote
orders        taken at the top of each loop: hold/lift → holds · bump → priority 0
              retry → deferred|failed → queued · redo → the named step re-runs although done()

explicit      uv run python episode.py <book> <n>     claims that one row (works today, unchanged)
no unit       uv run python episode.py <book>          drains queued rows in priority, sequence order
not built     a worker loop that starts a five-hour GPU job unattended — a queued row is a REQUEST
              until the owner says it is an instruction
